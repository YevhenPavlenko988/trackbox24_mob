# TrackBox24 Mobile

Робочий застосунок **представника** й **водія** [TrackBox24](https://trackbox24.com): сканування посилок (отримання з Нової Пошти, завантаження в машину, видача клієнту, на склад), рейси, офлайн-черга сканів. Менеджери й адміністратори працюють у вебі (`trackbox24_web`); їм застосунок показує сторінку «користуйтесь веб-версією».

**Стек:** Flutter 3.47 / Dart 3.13, Riverpod 3, go_router, dio, flutter_secure_storage, drift (офлайн-черга), mobile_scanner, freezed + json_serializable, ARB-локалізація (лише `uk`).

## Запуск

Потрібен запущений бекенд (`trackbox24_back`, `docker compose up -d`) на `:8080`.

```bash
flutter pub get
dart run build_runner build --delete-conflicting-outputs   # freezed / json / drift / riverpod
flutter gen-l10n                                            # також запускається автоматично при build/run

# iOS-симулятор: localhost працює напряму
flutter run --dart-define=FLAVOR=dev --dart-define=API_BASE_URL=http://localhost:8080

# Android-емулятор: хост доступний як 10.0.2.2
flutter run --dart-define=FLAVOR=dev --dart-define=API_BASE_URL=http://10.0.2.2:8080

# фізичний пристрій у тій самій Wi-Fi-мережі
flutter run --dart-define=FLAVOR=dev --dart-define=API_BASE_URL=http://192.168.x.x:8080
```

## Реліз у TestFlight

```bash
# підняти номер білда в pubspec.yaml (version: X.Y.Z+N), далі:
tool/release_ios.sh
```

Скрипт збирає з потрібними `--dart-define`, перевіряє, що адреса прода справді потрапила в ipa, і завантажує білд.

Підпис і завантаження йдуть через ключ App Store Connect API з роллю **Admin** (лише Admin може користуватися хмарним
сертифікатом iOS Distribution), тож входити в Xcode під Apple ID не потрібно. Файл ключа — `~/.appstoreconnect/private_keys/AuthKey_<KEY_ID>.p8`
(не в репозиторії); Key ID та Issuer ID — у скрипті, їх можна перевизначити `ASC_KEY_ID` / `ASC_ISSUER_ID`. Потрібен повний Xcode
(`xcode-select -p` → `/Applications/Xcode.app/...`).

**Без `--dart-define` збірка виходить у `dev`-флейворі й дивиться в `http://localhost:8080`** — на телефоні це «Немає зв'язку із сервером». Перевірити зібране можна в застосунку: «Ще» → «Версія» показує флейвор.

`FLAVOR` = `dev` | `prod` (за замовчуванням `dev`). У `dev` дозволено `http://` (Android `debug/res/xml/network_security_config.xml`, iOS `NSAllowsLocalNetworking`), у налаштуваннях видно адресу сервера. Prod без `API_BASE_URL` використовує `https://api.trackbox24.com`. У `dev` на екрані «Ще» можна тимчасово перевизначити адресу сервера (зберігається в Keychain/Keystore) та очистити чергу сканів.

## Android APK

```bash
# підняти номер білда в pubspec.yaml, далі:
PATH=$HOME/development/flutter/bin:$PATH tool/release_android.sh   # → build/trackbox24-X.Y.Z.apk
```

Підписаний прод-APK, щоб роздати файлом (без Google Play; на телефоні — дозволити встановлення з невідомих джерел).
Оновлення ставиться поверх лише з тим самим ключем і більшим номером білда.

- Ключ (upload keystore) — поза репозиторієм: `~/.android-keys/trackbox24.jks` (або `ANDROID_KEYSTORE`), alias `upload`
  (або `ANDROID_KEY_ALIAS`). Паролі — у Keychain: `trackbox24-android-store` (сховище) і, якщо інший, `trackbox24-android-key`
  (`security add-generic-password -s <назва> -a trackbox24 -w`). `android/key.properties` скрипт пише лише на час збірки.
  **Ключ і паролі — тримати резервну копію: без них оновлення вже встановленого застосунку неможливе.**
- Скрипт перевіряє, що APK підписано не debug-ключем і що в ньому адреса прода.
- Потрібні Android SDK (`brew install --cask android-commandlinetools`, далі `sdkmanager` у `~/Library/Android/sdk`:
  `platforms;android-36`, `build-tools;36.0.0`, `platform-tools`, `ndk;28.2.13676358`) і JDK 17
  (`flutter config --android-sdk ~/Library/Android/sdk --jdk-dir "$(/usr/libexec/java_home -v 17)"`).

Ідентифікатори застосунку: Android `ua.trackbox24.app`, iOS `ua.trackbox24.app`; назва «TrackBox24».

Тестові облікові записи з локального сіду вебу: `rep@test.ua` / `rep12345` (REPRESENTATIVE); водія створює менеджер у вебі.

## Сценарії на симуляторі

`integration_test/` проходить екрани застосунку в iOS-симуляторі проти локального бекенду й зберігає скриншоти в
`build/screenshots/` (драйвер `test_driver/integration_test.dart`). Потрібні Xcode (`xcode-select -s /Applications/Xcode.app/...`),
запущений бекенд і дані: представник у компанії з модулем «Переїзди» та переїзд щонайменше з трьох місць (сценарій видаляє одне).

```bash
flutter drive --driver test_driver/integration_test.dart --target integration_test/move_edit_test.dart \
  -d <id симулятора> --dart-define=FLAVOR=dev --dart-define=API_BASE_URL=http://localhost:8080 \
  --dart-define=E2E_REP=rep-sim@test.ua --dart-define=E2E_MOVE=M123456
```

`move_edit_test.dart`: вхід, вкладка «Переїзди», картка, редагування переїзду, опис і видалення місця, «Черга» в «Ще».
`move_load_test.dart`: водій (`E2E_DRIVER`, `E2E_TRIP_ID`, `E2E_TRIP`) вантажить переїзд зі «Завантажити» рейсу — відкривається
екран переїзду; потім нагадування «Усе завантажено» і, після вивантаження на склад (`E2E_WAREHOUSE_ID`), «Машина порожня» → «Завершити».
`seat_move_test.dart`: вибране місце «На склад» без сканування (`E2E_WAREHOUSE`, за замовчуванням «варшава»); з
`--dart-define=E2E_REFUSED=true` менеджер на час спроби кладе переїзд у кошик, і вікно має показати відмову сервера в собі
(помилка у вікні, а не снекбаром під ним — інакше «нічого не відбувається»).
`parcel_pay_test.dart`: водій (`E2E_DRIVER`) вводить код посилки `E2E_PARCEL` за 30 €, бачить ціну в інших валютах, укр. картка —
гривня й «До сплати», закордонна — без гривні, списує всі бали клієнта («Реферальна програма») і видає з оплатою в гривнях.
`currency_test.dart`: «Ще» → «Курси валют», представник встановлює курс долара, оплата переїзду (`E2E_MOVE` з ціною в євро) у доларах
з перерахунком, переїзд у доларах, вибір валюти рахунку, повернення курсу банку. Компанії потрібен модуль «Курси валют» і жодного власного курсу на старті.
`photo_upload_test.dart`: водій (`E2E_USER`, `E2E_PASSWORD`) вводить код `E2E_PARCEL` → «Фото» → «З галереї»; системну галерею
тест не проходить — фото вибирає людина (у Xcode 27 симулятор показує DeviceHub), тест чекає до 3 хв. Перед прогоном
`xcrun simctl addmedia <id> <фото 48 Мп>`; бекенду — фото увімкнені (S3, напр. `adobe/s3mock`) і модуль фото в компанії.
Перший сценарій — фото завантажено (на сервері 2048 px); другий — водій виходить із фото посеред завантаження, а воно
довантажується й з'являється «Фото додано». Щоб устигнути вийти, `API_BASE_URL` через проксі з повільним вивантаженням.
Скриншоти `binding.takeScreenshot` у симуляторі виходять заставкою; живі екрани — `xcrun simctl io <id> screenshot` під час прогону.

## Друк етикеток

Етикетки друкуються напряму на **NIIMBOT B3S_P** (B3S, 203 dpi, голівка 576 точок) по Bluetooth LE — без застосунку NIIMBOT і без офіційного SDK. Протокол реалізовано самостійно в `features/printer/niimbot/` за відкритими описами (niimbluelib, hass-niimbot): кадр `55 55 CMD LEN DATA XOR AA AA`, послідовність «B1» (`SetDensity → SetLabelType → PrintStart(7 б) → PageStart → SetPageSize(6 б) → рядки → PageEnd → опитування PrintStatus → PrintEnd`), рядки 1 біт/точка з повторами, порожні рядки — `PrintEmptyRow`, до 6 точок — `PrintBitmapRowIndexed`. Bluetooth — `universal_ble` (BSD, Swift Package Manager; `flutter_blue_plus` 2.x вимагає комерційну ліцензію, а 1.x конфліктує з `connectivity_plus` через `dbus`).

- **Налаштування:** «Ще → Принтер етикеток» — пошук принтерів поруч (у списку — пристрої з іменами виду `B3S_P-…`; перемикач «Показати всі пристрої» на випадок іншого імені), збереження обраного (Keychain/Keystore), щільність 1–5 (стандартно 3), пробна етикетка з Code 128.
- **Рулон:** у клієнта рулон 50 мм, етикетка 70 мм лежить уздовж стрічки — зображення 70×50 друкується повернутим на 90° (проти годинникової: текст читається знизу вгору, як виходить з принтера). У налаштуваннях принтера — ширина рулону 40 / 50 / 70 мм (70 — етикетка 70×40 упоперек, без повороту) і «Зсув по ширині» ±6 мм. Сторінка завжди на всю ширину голівки (576 точок), зображення по центру: принтер не розміщує вужче зображення сам, а рулон тримається посередині голівки.
- **Друк:** на екрані етикетки «Надрукувати (N)» — одне підключення, одна сторінка на місце; шит показує хід і текст помилки принтера (відкрита кришка, немає стрічки, розряджений, зайнятий застосунком NIIMBOT…). Без обраного принтера кнопка веде в налаштування. «Поділитися» лишається як запасний шлях.
- **Особливості:** на iOS відповіді принтера приходять із зайвим байтом перед `55 55` і бувають розрізані між нотифікаціями — `NiimbotPacketReader` це збирає; записи йдуть без відповіді шматками по MTU−3. Застосунок NIIMBOT тримає принтер зайнятим — його треба закрити.
- **Швидкість:** етикетки малюються, поки встановлюється зʼєднання; рядки зображення (≈230 пакетів на етикетку 70×50)
  ідуть по кілька в одному записі Bluetooth, до MTU−3 байт, рядок ніколи не розрізається, пауза 10 мс — після запису, а не після
  кожного рядка (було: запис і пауза на кожен рядок, ≈15 с до початку друку). На Android просимо швидкий інтервал з'єднання
  (`requestConnectionPriority(highPerformance)`, 7.5–15 мс замість 30–50).
- **Хронометраж:** після кожного друку (і невдалого) застосунок у фоні шле `POST /api/print-timings`: зʼєднання, передача й друк
  першої етикетки в мс, кількість, платформа, версія, принтер, заряд, помилка — на сервері це лише рядок у лозі (Grafana:
  `Label print on …`). Час останнього вдалого друку видно в «Ще → Принтер етикеток».
- **Перевірка без принтера:** `flutter test test/features/printer` — кадрування й контрольна сума (вектор з офіційного застосунку), збирання пакетів, кодування рядків, повна послідовність друку проти фейкового B3S (`FakeB3S`), рядки по кілька в записі, помилка принтера, тайм-аут. Друк на реальному B3S_P ще не підтверджено.

## Маршрути (рейс із плечима)

Пошук у списках посилок і переїздів (підказка «Код, ТТН, ім'я або телефон») іде через `GET /api/parcels?query=` — бекенд шукає й за ПІБ та телефоном клієнта. Картки списків (`ListCard`: рейс, посилка, переїзд) — окремі плитки з рядками з іконками (платне зберігання на НП — червонуватий фон і червона смуга зліва). Картка рейсу: маршрут, виїзд, машина й водії, рядок «Завантажено N з M» (`loadedCount` / `plannedCount`, понад план — «Завантажено N, за планом M»), «видано N»; під нею переїзди рейсу (`moves`: код · клієнт · опис · місць; ті, що поїдуть цим плечем пізніше, — курсивом «далі, зараз на плечі N»). Посилка/переїзд: код і кількість місць, «відправник → клієнт» (одне ім'я, якщо це та сама людина), опис, для переїзду — міста, далі стан і гроші НП, внизу тег рейсу. Склади у виборі (завершення рейсу,
«На склад», склад у рахунку) читаються щоразу при відкритті — доданий на вебі склад видно без перезапуску застосунку
(сценарій `new_warehouse_test.dart`).

«Наступне плече» є на будь-якому своєму рейсі водія (з модулем «Переїзди»): `POST /api/trips/{id}/next-leg` — рейс сам
по собі стає плечем 1 нового маршруту з тим самим номером (№36 → №36.1), нове плече — №36.2, вантаж після складу планується
на нього. Переїзд, створений водієм, після етикеток просить рейс: свої відкриті або «Новий рейс» (кнопка у виборі рейсу,
«звідки → куди» з переїзду). Сценарій `next_leg_test.dart` (`E2E_TRIP`; у водія має бути закріплена машина).

Картка рейсу водія нагадує, чого рейс чекає (`reminder` з `GET /api/trips/{id}`): «Не все завантажено» з кнопкою «Завантажити» (`LOAD`: у плані є незавантажене; «Виїхав» тоді показує одне попередження і три кнопки одна під одною: «Сканувати», «Виїхати без них», «Скасувати»); «Усе завантажено» з кнопкою «Виїхав» — усе з
плану в машині й кожне місце відскановано; «Машина порожня» з «Завершити» — усе вивантажено на склад чи видано. Плече, на якому
не позначили «Виїхав», теж завершується цією кнопкою — бекенд сам запише виїзд. Місце переїзду, відскановане будь-яким сканером
(«Завантажити» з рейсу, вкладка «Сканувати»), відкриває екран переїзду (`MoveScanScreen` з `code`) — прогрес «N з M» і що ще не
відскановано, а не вікно посилки; з рейсу — одразу завантаження в нього. Рейс у кнопках і підписах — за номером (`№14.2`), не за id.

Плече маршруту — звичайний рейс водія, підписаний «№14.2» (`Trip.shownNumber`, `legNo`); у картці — «Плече: Рейс №14 · плече 2»
блок «Плечі рейсу» — усі плечі з машиною, водієм, датою й станом (`GET /api/routes/{id}`, `RouteLegsSection`): свої
виділені кольором і відкриваються, плече, що зараз вантажиться чи в дорозі, — в рамці (чиє б не було), чужі — лише для перегляду; і кнопка «Наступне плече» (`/trips/new?routeId=&leg=&from=` → `POST /api/routes/{id}/legs`, звідки — куди прибуло це плече).
Новий рейс можна одразу зробити першим плечем маршруту (перемикач «Рейс у кілька плечей» → `POST /api/routes`; лише з модулем «Переїзди»). Після
вивантаження на склад вантажу маршруту результат скану (і екран сканування переїзду) підказує, куди далі: «Далі — плече 14.2:
AA1234, Іван» або «Наступного плеча ще немає — чекає на складі» (`NextLegHint`).

## Вантажники, склад і оплати переїзду

Оплати, які клієнт зробив сам на сторінці відстеження (модуль «Онлайн-оплата» на бекенді), приходять зі способом
`ONLINE` («Онлайн-оплата») чи `TRANSFER` («Переказ на рахунок», підтвердив менеджер) і показуються як є; вибрати їх у
застосунку не можна.

У картці переїзду під місцями — блок «Вантажники, склад, оплати» (`MoveBillSection`, `GET /api/parcels/{id}/bill`): підсумок
(перевезення, вантажники, склад, разом, оплачено, до сплати; вантажникам належить / виплачено), роботи завантаження й
вивантаження з вантажниками — тап на годинах вносить фактичні, галочка — «оплачено вантажнику», кошик з підтвердженням
видаляє роботу, внесену помилково (`DELETE …/works/{id}`), разом із вантажниками й годинами. У виборі вантажників роботи згори ті,
хто був вибраний на відкритті (і щойно доданий), решта стоїть на місці — галочка не пересуває список під пальцем. «Робота» (вид, коли, планові
години, ставки клієнту й вантажнику, вантажники з довідника з пошуком за ім'ям чи телефоном і фільтром за містом (спершу — місто роботи: звідки для
завантаження, куди для вивантаження) — вибрані вгорі, «Новий вантажник» прямо тут), «Оплата» (передоплата чи решта),
«Склад» (склад, днів × ставка; «Новий склад» прямо тут), валюта розрахунку (€ / грн), «Рахунок» — Excel-файл рахунку (`GET …/invoice.xlsx`, той самий, що на вебі) у будь-який месенджер; без зв'язку — той самий рахунок текстом. У роботі на кожного вантажника «План N год», «Факт: внести» / «Факт N год», «Не виплачено» / «Виплачено ✓» і «вантажнику N €»; під роботою окремо «Вантажникам» і «Клієнту». Редагують водій і представник.

Новий склад на ходу (`createWarehouse`) — у кожному виборі складу: скан на склад, ручне переміщення, зберігання.

## Реферальна програма

З модулем «Реферальна програма» (`referralEnabled` компанії): у формі клієнта — «Порадив» (вибір клієнта, канал стає
«Рекомендація»), у картці клієнта — «Порадив» і «Бали», у картці посилки — знижка за рекомендацією, списані бали й «До сплати».
У вікні видачі після скану під ціною — знижка й «до сплати»; вибраний спосіб оплати відкриває «Списати бали» (`PointsField`: є N,
можна до M, «Усі M»), «До сплати» зменшується, і валюта оплати рахується від нього. Те саме при прийомі посилки з оплатою
(`forNew` за ціною). Бали завжди клієнта посилки. Списані бали йдуть і в офлайн-черзі (колонка `pointsToRedeem`, схема 7).
Вікно видачі прокручується, коли з оплатою, балами й валютами воно вище за екран.

## Курси валют

З модулем «Курси валют» (`currencyEnabled` компанії) у «Ще» є «Курси валют» (`RatesScreen`, `/rates`): курс, що діє, звідки він
(курс компанії — хто й коли встановив, або продаж банку), і курс Monobank / ПриватБанку з часом. Представник встановлює курс компанії
(олівець) і повертає банківський; водій лише бачить. В «Оплата» переїзду — валюта грн / € / $ / zł з перерахунком у валюту
переїзду (курс фіксується на момент оплати); в оплатах «100 $ → 91,07 €». «Рахунок» спершу питає валюту, і Excel чи текст
рахунку йде в ній (`?in=`) з рядком «Курс: 1 € = X $». Валюта самого переїзду з модулем — € / грн / $ / zł (`priceCurrencies`), без
нього € / грн. Порядок усюди: €, грн, $, zł (`moneyCurrencies`). Перемикання валюти переїзду питає підтвердження з курсом —
ціни перераховуються. Під оплатою в іншій валюті — «за курсом 1 $ = 0,8899 €». У верхній панелі вкладок (переїзди, посилки,
рейси, сканування) — іконка курсів (`RatesAction`): знизу курси для оплат, джерело й «Усі курси».

В історії рейсу у «Видано» — що взяли за посилку: «Оплачено: Укр. картка · 1 552,79 грн (30 €)». Без курсу вибір валюти
видно, але вибрати можна лише валюту ціни, з підказкою «Курсу ще немає».
Уже оплачена посилка у вікні видачі не пропонує вибір оплати — лише як її оплатили («Укр. картка · 1 552,79 грн за курсом …»).
Посилки: у вікні видачі після скану під ціною — вона в інших валютах (`PriceInCurrencies`), а вибраний спосіб оплати відкриває
валюту (`PaidCurrencyPicker`): укр. картка — гривня за замовчуванням, закордонна — без гривні, готівка — будь-яка; «До сплати:
1 552,79 грн (1 € = 51,7598 грн)». Те саме при прийомі посилки з оплатою. Валюта йде в скан (`paidCurrency`), і в офлайн-черзі
теж (колонка `paidCurrency`, схема 6). У картці посилки — «Валюта оплати». Ціна посилки з модулем — і в USD/PLN.

## Офлайн-черга

Скани `receive` / `load` / `deliver` / `toWarehouse`, які не вдалося відправити через відсутність зв'язку (connection error / timeout), зберігаються в SQLite (`scan_queue_items`, drift) і відтворюються воркером **строго в порядку сканування**: при появі мережі (`connectivity_plus`), при поверненні застосунку на передній план, після успішного онлайн-скану або кнопкою «Синхронізувати». Транспортна помилка повертає запис у чергу і зупиняє прогін (щоб не обігнати `load` → `deliver` одного місця), далі backoff 2с·2ⁿ ≤ 60с. Відповідь 4xx позначає запис `failed` із `detail` бекенду і каскадно «валить» наступні скани того ж коду; `failed` можна повторити або видалити на екрані «Черга». 401 зупиняє прогін до нового логіну. Пошук (`lookup`) ніколи не ставиться в чергу; дубль (той самий режим + код) відхиляється. Посилки з очікуваним сканом помічаються «скан у черзі» в списках.
Кожен скан черги належить тому, хто сканував (`userId`): інший користувач на цьому телефоні його не бачить і не відправляє; вихід
з акаунта прибирає відправлені (історію), невідправлені чекають наступного входу того ж користувача. Успішна відправка стирає
стару помилку.

**Дані для роботи без зв'язку** (`core/api/offline_cache.dart`): останні відповіді на `GET /api/trips`, `/api/trips/{id}`,
`/api/trips/{id}/parcels`, `/api/warehouses`, `/api/parcels/{id}`, `/api/companies/current` лежать у `cached_responses` і
віддаються замість помилки, коли зв'язку немає, — вибір рейсу й складу та картка посилки чи переїзду відкриваються в режимі
польоту. Поки є мережа, `OfflineWarmUp` сам наповнює збережене: відкриті рейси водія (до 20) з посилками й переїздами, рейси
для завантаження, склади, компанія — після входу, при поверненні зв'язку, при поверненні в застосунок і раз на 15 хв (не
частіше ніж раз на 2 хв). Картка кожної посилки зі списку (рейсу чи вкладки) зберігається окремо, тож відкривається офлайн, навіть
якщо її не відкривали. Вихід із акаунта очищує збережене. Транспортну помилку Riverpod повторює лише двічі, щоб нічого не «висіло».
Офлайн дії визначає сам код: наш штрихкод — завантаження / склад / видача, ТТН — ще й отримання (представнику).

## Фото посилок

До 3 фото на посилку (`features/parcels/ui/parcel_photos.dart`): блок у картці посилки, окремий екран `/parcels/:id/photos` з результату скану. Кнопки видно лише коли `photosEnabled` у `GET /api/companies/current` (`photosEnabledProvider`, запитується раз після логіну); без цього блок показує лише вже додані фото. Телефон зменшує фото до 2048 px по довшій стороні (JPEG 85, `features/parcels/data/photo_pick.dart`) — сервер однаково зберігає не більше 2048 px, а оригінал камери на повільному зв'язку обривався; файли йдуть одним `multipart`, конвертує сервер у WebP, усі або жодного; таймаут запиту 3 хв. Посилання presigned на годину, картинки кешуються за `thumb-<id>` / `photo-<id>`. В офлайн-чергу фото не входять.

## Переїзди

Переїзд — посилка з `kind: MOVE` (модуль компанії «Переїзди»): багато місць з кодами `M123456-N` і описом кожного. У картці
переїзду — список речей (опис, код, статус, фото) і «Сканувати переїзд»: етап «Завантаження в машину» (вибір рейсу), «Прийом
на склад» (вибір складу) або «Видача отримувачу», далі `MoveScanScreen` — сканування етикеток у будь-якому порядку без питань
на кожну, лічильник «X з N» і список того, що лишилось; чужі коди й повтори не надсилаються. Скани йдуть звичайними
`/api/scan/load|to-warehouse|deliver` і без зв'язку потрапляють в офлайн-чергу. «Закінчили сканування» питає бекенд
(`GET /api/parcels/{id}/seats/check`) і показує, чого бракує; «Записати підсумок» — `POST …/seats/check` (неповна видача —
лише з коментарем). Без зв'язку підсумок показується з того, що відскановано на телефоні, і не записується. Фото місця —
до 3 на кожне (`?seatNumber=N`), блок «Фото» показує лише фото всієї посилки. Етикетка NIIMBOT переїзду: «17/120» великим,
маршрут «звідки → куди», отримувач і його телефон, опис у два рядки й код зі штрихкодом. Без модуля «Переїзди» (`movesEnabled` у
`/api/companies/current`) картка переїзду лише для перегляду: немає «Сканувати переїзд», а фото місць додаються,
тільки якщо ввімкнені «Фото».
Блок «Дані переїзду» — без ваги, габаритів, оголошеної вартості, представника, рейсу й плану (де кожне місце — у розділі місць).

Переїзд на місці (`MoveFormScreen`, `/moves/new[?tripId=]`): у картці рейсу водія кнопка «Додати переїзд у рейс» (ще один переїзд у цей рейс і його маршрут — не
новий рейс), «+» у списках і в
«Рейсах» — посилка чи переїзд за модулями компанії (`startNewShipment`). У «Рейсах» водія дві підписані кнопки: «Новий рейс» і
«Прийняти переїзд» / «Прийняти посилку» за модулем, а з обома модулями — «Прийняти…» з вибором. Форма: відправник (клієнт, необов'язково) і отримувач (клієнт, обов'язково), звідки, куди (з їхніх міст), опис, речі
рядками або кількістю (до 500) → `POST /api/parcels` з `kind: MOVE` → картка, етикетки, далі скан завантаження в рейс: з картки рейсу — в нього, з «+» — у вибраний одразу після етикеток.
«Додати речі» в картці переїзду → `POST /api/parcels/{id}/seats`, далі друк лише нових (`/parcels/{id}/label?from=N`).
«Додати й друкувати» (`move_quick_add.dart`): по одній речі — місце створюється й етикетка одразу йде на NIIMBOT без перегляду,
поле очищується для наступної; без налаштованого принтера спершу відкриваються його налаштування.
«Реєстр» у блоці місць: `GET /api/parcels/{id}/seats/register.xlsx` → тимчасовий файл `<код>-seats.xlsx` → системне «Поділитися»
(Viber, Telegram, WhatsApp, пошта), з текстом «Реєстр місць переїзду M…».

Ручне переміщення без сканування (зірвана етикетка, не працює камера): чекбокси біля місць, панель «Вибрано: N» з «На склад»
(вибір складу) і «Видати» (лише водій) → `POST /api/parcels/{id}/seats/move`; неповна видача — з коментарем. Без модуля
«Переїзди» чекбоксів немає. В історії — «Без сканування».

### Вибрані місця без сканування

Галочки в картці переїзду: кнопки лише ті, що бекенд дозволить для всіх вибраних місць і цієї ролі (`canMoveToWarehouse`,
`canHandOver`, `canLoadByHand`). Місце на складі — «У рейс №14.2» (рейс, у плані якого переїзд; без плану — «У рейс…» з вибором рейсу; `POST
…/seats/move` з `target: LOAD` — як введений вручну скан завантаження), «Видати» (водій, представник, менеджер) і «На інший склад» (лише менеджер);
у машині — «На склад» і «Видати»; немає жодної дії — підказка сканувати. Сценарій `seat_load_test.dart` (`E2E_TRIP`, `E2E_MOVE`).

### Редагування переїзду

Кнопка «Редагувати» в картці переїзду відкриває ту саму форму, що й створення (`MoveFormScreen(parcel:)`, `/parcels/:id/edit-move`):
відправник, отримувач, звідки, куди, опис. На сервер іде лише змінене (`PUT /api/parcels/{id}`, часткове оновлення); новий відправник
приносить ім'я, телефон і місто зі своєї картки. Місця редагуються в картці: меню «⋮» у рядку місця — «Змінити опис»
(`PUT …/seats/{n}`) і «Видалити місце» (`DELETE …/seats/{n}`, разом із фото; лише поки всі місця ще в нас і їх більше одного, як на
бекенді). Номери інших місць не змінюються — надруковані етикетки лишаються правильними; нові місця отримують номери після найбільшого.

### Вкладка «Переїзди»

Представник компанії з модулем «Переїзди» має вкладку «Переїзди» (`MovesListScreen`, гілка 7, `/rep/moves`): усі переїзди компанії,
нові згори (`GET /api/parcels?kind=MOVE&sort=createdAt,desc`), пошук і чипи «В роботі» (отримані, прийняті водієм, на складі, у машині) /
«Видані» / «Усі»; «+» створює переїзд. У нижній панелі вміщається п'ять вкладок, тож у такого представника «Черга» переїжджає в «Ще»
(`queueInMore`): пункт «Черга» з лічильником угорі другого блоку, і бейдж невідправлених сканів стоїть на «Ще». Без модуля й у водія
вкладки як раніше.

### Компанія лише з переїздами

Без модуля «Посилки» (`parcelsEnabled: false` у `/api/companies/current`; невідомо — вважається ввімкненим) у представника немає
вкладки «Забрати» (оболонка сама переходить на першу вкладку), у списках немає кнопки «Нова посилка», у водія в «Рейсах» — «Прийняти
посилку». Нову ТТН, відскановану представником, бекенд відхиляє з поясненням.

## Нюанси бекенду

- Вкладка «Прийняті» у чистого водія — `GET /api/parcels?status=ACCEPTED_BY_DRIVER&sort=statusChangedAt,desc`: чип «Мої» додає `mine=true` (бек віддає лише прийняті цим водієм), «Усі» — прийняті будь-яким водієм компанії. У користувача з обома ролями прийняті водієм посилки вже є в «Отримані», і окремої вкладки немає. Чипи у `ParcelListScreen` бувають двох видів: `test` сіє завантажене на клієнті, `adjust` міняє серверний запит.

- JWT без refresh (TTL 12 год); токен відкликається при зміні пароля/ролей/деактивації → будь-який 401 = вихід на логін з позначкою «сесія завершилась». Термін дії зберігається поруч із токеном, протермінований не використовується.
- Свій пароль: «Ще» → «Змінити пароль» → `POST /api/auth/password` (потрібен поточний, мінімум 8 символів). Відповідь — новий токен, який одразу зберігаємо, інакше наступний запит викинув би користувача з власної сесії; інші пристрої виходять. Стан `authProvider` при цьому не чіпаємо — його зміна перебудовує роутер і екран, що саме закривається.
- Помилки — RFC 7807 (`title`, `detail`, `errors{field}`, додаткові поля як `extensions`, напр. `undeliveredParcels` на 409); 401/403 від Spring Security — з порожнім тілом.
- `null`-поля у відповідях пропускаються — усі поля моделей опціональні, крім `id`/`email`.
- Чистий DRIVER не має доступу до `GET /api/parcels` — посилки лише через скан-пошук і списки рейсу.
- Водій приймає посилку від людини: `POST /api/parcels` без `npTtn`, клієнт обов'язковий (`GET /api/clients?search=` або `POST /api/clients`), ціну доставки водій може вказати — представник ні. Поруч із ціною — «Оплачено зараз» (`paymentMethod`: `CASH` / `UA_CARD` / `FOREIGN_CARD`): посилка створюється одразу оплаченою, прийняв оплату — водій; без ціни метод не надсилається. Тип вантажу НП («Посилка» / «Документи» / «Вантаж») водій обирає одразу під описом — від нього залежать правила: опис і оголошена вартість (> 0) обов'язкові завжди, вага > 0 — для посилки й вантажу, для документів вага необов'язкова, але не більше 1 кг (бек округлює до 0,1 / 0,5 / 1 кг і не передає габарити); габарити 0,1–9999 см. Тип іде в `PUT …/np-shipment` разом з отримувачем. Редагувати посилку (разом з ціною доставки) водій може, поки вона «Прийнято водієм», «На складі» або «В машині» — олівець у картці лише в цих статусах; в інших бек відповідає 403. Замість відправника водій вказує отримувача (ПІБ одним полем і телефон) — одразу після створення вони йдуть у `PUT …/np-shipment`, і застосунок відкриває екран відправки поверх картки посилки. Така посилка одразу в статусі `ACCEPTED_BY_DRIVER` («Прийнято водієм»), далі як отримана представником.
- «Додати в рейс» у картці посилки (водій, посилка в наших руках і ще не в машині): шит зі своїми рейсами, у які ще можна вантажити (`PLANNED` / `PREPARING`), і «Новий рейс» (екран створення повертає рейс, `?pick=1`). Планувати в рейс (`POST /api/trips/{id}/parcels`) може лише менеджер, тому водій саме завантажує: кожне місце через `ScanService.perform(load)` — з офлайн-чергою й усіма правилами бекенду (свій рейс, призначені машина й водій, рейс ще не виїхав). У рейс, що вже в дорозі, додати не можна — водій створює новий.
- Зворотні посилки: `PUT /api/parcels/{id}/np-shipment` **замінює всі поля** (форма йде цілком) і працює, поки посилка в нас. ЕН створює водій (`POST …/np-shipment/waybill`, кнопка «Зберегти і створити ЕН» на екрані відправки або «Створити ЕН» у картці), після чого дані заморожені; помилку (список, чого бракує, або відмову НП, яку бек уже перекладає українською) показуємо як є. Під відділенням — його ліміт ваги з НП (і в списку пікера); якщо посилка важча — червоне попередження, що НП не створить ЕН. Доки НП не прийняла посилку, водій може «Видалити ЕН», виправити дані й створити знову. У відповіді `shipDate` — дата відправки в ЕН. Довідники `/api/nova-poshta/*` ходять у НП живим запитом ключем компанії — без ключа 400, і пікер показує цей текст. НП обмежує частоту запитів, тому пошук у шиті іде через 400 мс після останньої літери, а не на кожну.
- Етикетка 70×50 мм (`/parcels/:id/label`, іконка принтера в картці; висота за шириною рулону з налаштувань принтера): малюємо самі (`features/parcels/label/`) на 560×400 точок (8 точок/мм, NIIMBOT B3S) — три смуги: номер ЕН (останні чотири цифри жирним) з її Code 128, отримувач / місто з телефоном / відділення чи адреса з вагою праворуч, і внизу Code 128 `PT…`/`PT…-N` місця з номером місця; штрих модуля завжди ціле число точок. Одна етикетка на місце. «Надрукувати» друкує напряму на NIIMBOT по Bluetooth (див. «Друк етикеток»); «Поділитися» рендерить PNG і віддає в системне меню — звідти у застосунок NIIMBOT.

- iOS збирається лише для iPhone (`TARGETED_DEVICE_FAMILY = 1`): iPad-скриншоти для App Store не потрібні, інтерфейс розрахований на телефон.
